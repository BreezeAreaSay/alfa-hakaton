# API

REST API кредитного конвейера: кабинет клиента, рабочее место аналитика и администрирование демо-стенда работают через один API. Изменения по заявке приходят в интерфейс потоком событий (SSE). Процесс и статусы описаны в [process.md](process.md), правила решения — в [credit-policy.md](credit-policy.md).

Все примеры ниже сняты с работающего стенда. Ответы сокращены: показаны ключевые поля, остальные опущены.

## Аутентификация и роли

Вход — `POST /api/auth/login` с логином и паролем. В ответе JWT (HS256, действует 12 часов), его передают в заголовке `Authorization: Bearer <token>`. Демо-пользователи и их сценарии перечислены в [README](../README.md#сценарий-проверки), пароль у всех — `demo`.

Вход защищён от перебора паролей: после пяти неверных паролей по одному логину с одного адреса вход блокируется на 5 минут — метод отвечает 429 с заголовком `Retry-After` и текстом «Слишком много попыток входа. Повторите через 5 минут». Успешный вход обнуляет счётчик; другие логины и другие адреса не затрагиваются. Каждая неудачная попытка записывается в журнал действий (`LOGIN_FAILED`: логин, адрес, срок блокировки). Пороги задаются переменными `LOGIN_ATTEMPTS` и `LOGIN_WINDOW_SECONDS`, сброс демо-данных снимает блокировки.

```http
POST /api/auth/login
Content-Type: application/json

{"login": "veter", "password": "demo"}
```

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5…",
  "user": {
    "id": "7f052893-dc43-4df5-a22b-91718eb8c9fd",
    "login": "veter",
    "full_name": "Ветров Андрей Сергеевич",
    "role": "CLIENT",
    "can_sign": true,
    "company": {"inn": "0010000017", "name": "ООО «Северный ветер»"}
  }
}
```

| Роль | Демо-логины | Что доступно |
|---|---|---|
| Без входа | — | Вход, каталог продуктов, справочники, подбор продукта, проверки `health` и `ready` |
| `CLIENT` | `veter`, `smirnova`, `tehnomaster`, `orlov`, `vektor`, `romashka`, `grand`, `start`, `altair`, `meridian` | Профиль своей компании, заявки, документы, ответы на запросы банка, предложения, подписание, кредит, чат, уведомления, разбор описания задачи |
| `UNDERWRITER` | `analyst`, `analyst2` | Рабочее место банка `/api/bank/*`, карточка и документы любой заявки, чат, уведомления банка, просмотр состояния внешних систем и журнала действий, ИИ-сводка досье |
| `ADMIN` | `admin` | Всё, что доступно аналитику, плюс сброс демо-данных и управление сбоями внешних систем |

Правила доступа:
- **Клиент видит только заявки своей компании.** Чужая заявка, документ, предложение или запрос возвращают 404 «Заявка не найдена» — API не раскрывает, что объект существует.
- **Сотрудники банка видят заявки всех компаний.** Черновики в рабочее место банка не попадают: методы `/api/bank/*` возвращают для них 404.
- **Карточка заявки зависит от роли.** Клиенту приходят формулировки статусов для клиента, без технических ошибок шагов (`steps[].error`) и без причин переходов в истории (`history[].reason`). Сотрудник банка видит всё.
- **Методы чужой роли** возвращают 403 «Недостаточно прав». Подписать договор может только пользователь с правом подписи (`can_sign`), иначе 403.
- **Нет токена, он неверный или истёк** — 401 «Нужно войти заново» с заголовком `WWW-Authenticate: Bearer`.

## Соглашения

### Формат данных

- Запросы и ответы — JSON в UTF-8. Загрузка файлов — `multipart/form-data`.
- Идентификаторы заявок, предложений, документов, запросов информации, пользователей и кредитов — UUID. Номер заявки для людей — `number` вида `2026-00003`.
- Суммы и ставки в основных схемах — строки с двумя знаками после запятой (`"3000000.00"`, `"19.00"`), чтобы не терять точность. В запросах можно передавать число или строку. Числами приходят расчётные показатели в досье, `constraints` предварительного расчёта, разобранная выписка (`parsed`) и сумма в разборе описания задачи.
- Даты — `YYYY-MM-DD`, время — ISO 8601 в UTC: `2026-10-21T11:57:20.867479Z`.
- Коды (статусы, продукты, цели, типы документов) — латиницей в верхнем регистре. Подписи для людей — в полях `*_label` и в справочниках `GET /api/meta`.
- Списки без постраничной навигации, с фиксированным пределом: очередь банка — 300 заявок, уведомления — 50, журнал действий — 200 записей.

### Ошибки

Ошибка возвращается с телом `{"detail": "…"}`. Текст на русском и готов к показу пользователю:

```json
{"detail": "Без согласий на запрос в БКИ и обработку персональных данных мы не сможем рассмотреть заявку"}
```

Если запрос не прошёл проверку схемы (нет обязательного поля, неверный тип или значение не из списка), FastAPI возвращает 422, а `detail` — список нарушений:

```json
{
  "detail": [
    {
      "type": "literal_error",
      "loc": ["body", "action"],
      "msg": "Input should be 'APPROVE', 'COUNTER' or 'REJECT'",
      "input": "MAYBE",
      "ctx": {"expected": "'APPROVE', 'COUNTER' or 'REJECT'"}
    }
  ]
}
```

| Код | Когда |
|---|---|
| 200 | Успешный запрос |
| 201 | Создан черновик, загружен документ, отправлено сообщение в чат |
| 204 | Удалён черновик или документ, уведомления отмечены прочитанными. Тела нет |
| 401 | Нет токена, токен неверный или истёк; неверный логин или пароль при входе |
| 403 | Метод недоступен роли; нет права подписи |
| 404 | Объект не найден или принадлежит другой компании; черновик для сотрудника банка (черновик видит только клиент); неизвестная внешняя система; ИИ-сводка при выключенном ИИ |
| 409 | Действие недоступно в текущем статусе: «Заявка уже отправлена», «Предложение больше не действует», «Действие недоступно: заявка в статусе «Черновик»»; одновременное изменение заявки — «Заявка изменилась, обновите страницу» |
| 422 | Ошибка схемы запроса или бизнес-правила: сумма и срок вне продукта, нет согласий или залога, неверный пароль при подписании, выписка не разобрана, решение аналитика вне полномочий |
| 429 | Вход заблокирован после пяти неверных паролей; в заголовке `Retry-After` — через сколько секунд повторить |
| 503 | ИИ-сводка: модель не ответила |

Файл больше 12 МБ отклоняет nginx (413). Собственный предел API — 10 МБ (422 «Файл больше 10 МБ»). Непредвиденная ошибка сервера — 500 с текстом `Internal Server Error`.

### Идемпотентность: `Idempotency-Key`

Отправка заявки (`POST /api/applications/{id}/submit`) и подписание договора (`POST /api/applications/{id}/sign`) принимают заголовок `Idempotency-Key` — уникальную строку до 128 символов, например UUID; более длинный ключ отклоняется с кодом 422. Интерфейс создаёт новый ключ на каждое действие пользователя.

- Ключ запоминается после успешного действия, отдельно для пользователя, действия и заявки.
- **Повтор с тем же ключом** (двойной клик, повтор после обрыва связи) возвращает 200 и текущую карточку заявки. Действие не повторяется: конвейер не запускается второй раз (`run_no` не меняется), вторая подпись не создаётся.
- **Повтор без ключа или с новым ключом** проходит обычные проверки и получает 409: «Заявка уже отправлена» или «Договор сейчас нельзя подписать».
- **Неуспешная попытка не запоминается.** Например, после 422 «Неверный пароль» можно повторить подписание с тем же ключом.
- Заголовок необязателен, но без него повтор не отличить от новой попытки.

### Одновременные изменения

Действия с заявкой блокируют её строку в базе (`SELECT … FOR UPDATE`), а версия заявки (`version`) страхует от потерянных обновлений. Если аналитик принимает решение, а клиент в это же время отзывает заявку, пройдёт только первое действие. Второй участник получит 409: текст о недоступном действии («Решение можно принять только по заявке на ручном рассмотрении») или «Заявка изменилась, обновите страницу». После 409 интерфейс перечитывает карточку заявки.

### Идентификатор запроса: `X-Request-ID`

Каждый ответ содержит заголовок `X-Request-ID`. Клиент может передать свой идентификатор в этом же заголовке, иначе API создаёт его сам (16 шестнадцатеричных символов). Идентификатор пишется в JSON-логи `api` (поле `request_id`) и в журнал действий в базе (`audit_log.request_id`): по нему находят все следы конкретного запроса.

### Асинхронная обработка

Отправка заявки, ответ на запрос конвейера, принятие предложения, подписание и перезапуск проверки отвечают сразу, а работу выполняет обработчик `worker`. Заявка проходит промежуточные статусы:

| Действие | Промежуточный статус | Результат |
|---|---|---|
| Отправка, ответ на запрос конвейера, перезапуск | `SUBMITTED`, `IN_PROCESSING` | `OFFER`, `NEED_INFO`, `MANUAL_REVIEW` или `REJECTED` |
| Принятие предложения | `ACCEPTED` | `SIGNING`: договор сформирован |
| Подписание | `SIGNED` | `ISSUED`: кредит выдан |

На демо-стенде это занимает несколько секунд. Результат получают одним из способов: опрашивают `GET /api/applications/{id}` (раз в секунду достаточно) или слушают поток `GET /api/stream` и перечитывают карточку при событии с нужным `application_id`.

### CORS

На стенде интерфейс и API отдаются с одного адреса, CORS не нужен. Он разрешён только для дев-сервера Vite: `http://localhost:5173` и `http://127.0.0.1:5173`.

```http
Content-Type: application/json

{"text": "Выписка за 12 месяцев"}
```

```json
{
  "status": "IN_PROCESSING",
  "run_no": 2,
  "info_requests": [{"status": "ANSWERED", "answer_text": "Выписка за 12 месяцев", "answered_at": "2026-10-21T11:58:11.487059Z"}]
}
```

Ответ на запрос конвейера (`origin: "SYSTEM"`) запускает новый прогон проверки: выручка оценивается по выписке, и заявка Орлова через несколько секунд переходит в `OFFER`. Ответ на запрос аналитика (`origin: "UNDERWRITER"`) возвращает заявку тому же аналитику в `MANUAL_REVIEW`.

Ошибки: 422 «Приложите выписку по счёту в формате 1С или CSV», если запрошена выписка, а разобранной выписки нет; 422 «Добавьте ответ или приложите документ» — пустой ответ без документов; 409 «На этот запрос уже нельзя ответить» — запрос закрыт.

**5. Решение.** Только для заявки в `MANUAL_REVIEW`, иначе 409.

| `action` | Поля | Результат |
|---|---|---|
| `APPROVE` | `rate` и `comment` — необязательно | `OFFER`, предложение на запрошенных условиях (`kind: "AS_REQUESTED"`) |
| `COUNTER` | `product_code`, `amount`, `term_months`, `rate` — что меняется (остальное берётся из заявки), `comment` | `OFFER`, контрпредложение (`kind: "COUNTER"`, `note: "Условия предложены специалистом банка"`) |
| `REJECT` | `reason_code` (`R01`–`R07`) и `comment` обязательны | `REJECTED`, клиент видит причину по коду, для `R07` — текст комментария |

```http
POST /api/bank/applications/9769358c-ba00-4d64-8881-eb7d97bb5184/decision
Content-Type: application/json

{"action": "APPROVE", "comment": "Залог покрывает сумму, класс риска A"}
```

```json

    {"kind": "AS_REQUESTED", "product_code": "SECURED", "amount": "60000000.00", "term_months": 84, "rate": "15.50", "monthly_payment": "1174700.81", "status": "ACTIVE"}
  ],
  "history": [
    {"to_status": "MANUAL_REVIEW", "actor": "SYSTEM", "actor_name": null, "reason": "Продукт рассматривает аналитик"},
    {"to_status": "OFFER", "actor": "UNDERWRITER", "actor_name": "Иванова Ольга Дмитриевна", "reason": "Залог покрывает сумму, класс риска A"}
```

Полномочия аналитика ([credit-policy.md](credit-policy.md#полномочия-аналитика)) проверяются при решении, нарушение — 422 с текстом:
- сумма и срок — в границах продукта, ставка — не ниже расчётной;
- сумма выше расчётного лимита — только с комментарием и не больше чем на 20%. Предварительный расчёт наличие комментария не проверяет;
- отказ без причины или без комментария — 422 «Укажите причину отказа», «Добавьте комментарий к отказу».

Пример: у ООО «Вектор Логистик» лимит 5 650 000 ₽. `{"action": "COUNTER", "amount": 6000000, "term_months": 36}` вернёт 422 «Сумма выше расчётного лимита — добавьте комментарий с обоснованием»; с полем `comment` клиент получит контрпредложение на 6 000 000 ₽ под 20,5%.

## Управление демо-стендом

Методы для подготовки стенда к показу и проверки устойчивости конвейера.

**Сброс демо-данных** — `POST /api/admin/demo/reset`, только `ADMIN`. Удаляет заявки со всеми документами, событиями и ключами идемпотентности, очищает журнал действий, начинает нумерацию заявок заново и снимает сбои симулятора. Затем создаёт две демо-заявки — ООО «Вектор Логистик» и ООО «Гранд Девелопмент», — которые сразу проходят конвейер и через несколько секунд попадают к аналитику. Пользователи, компании и продукты сохраняются.

```json
{"status": "ok", "preseeded": 2}
```

То же из командной строки: `make reset` или `docker compose exec api python -m app.seed --reset`.

**Сбои внешних систем.** `GET /api/admin/simulator/faults` показывает режим каждой системы, `PUT /api/admin/simulator/faults/{source}` меняет его, `POST /api/admin/simulator/faults/reset` возвращает все системы в рабочий режим. Неизвестная система — 404. Ответ всех трёх методов — список систем:

```http
PUT /api/admin/simulator/faults/bki
Content-Type: application/json

{"mode": "error"}
```

```json
[
  {"source": "egrul", "title": "ЕГРЮЛ / ЕГРИП", "mode": "ok", "latency_ms": 0},
  {"source": "bki", "title": "Бюро кредитных историй", "mode": "error", "latency_ms": 0}
]
```

| `source` | Система | Где используется |
|---|---|---|
| `egrul` | ЕГРЮЛ / ЕГРИП | Шаг `EGRUL`, профиль компании |
| `fns` | ФНС «Прозрачный бизнес» | Шаг `FNS` |
| `girbo` | ГИР БО (отчётность) | Шаг `GIRBO` |
| `bki` | Бюро кредитных историй | Шаг `BKI` |
| `bank` | Внутренние данные банка | Шаг `BANK`, профиль компании |
| `core` | Выдача кредита (АБС) | Выдача после подписания |

| `mode` | Что делает симулятор | Что видит конвейер |
|---|---|---|
| `ok` | Отвечает с обычной задержкой | Шаг выполняется |
| `error` | Отвечает 503 | Шаг ждёт источник (`WAITING`) и повторяется через 2, 4, 8, 16, 30 секунд. После 5 ошибок подряд вызовы источника приостанавливаются на 20 секунд |
| `timeout` | Отвечает через 30 секунд | Вызов прерывается по таймауту 3 секунды, дальше — как при `error` |
| `slow` | Добавляет к задержке `latency_ms` (0–20 000 мс) | Если ответ дольше 3 секунд — как при `timeout` |

Пока источник недоступен, клиент видит «Ждём ответа бюро кредитных историй», заявка остаётся в `IN_PROCESSING` и не теряется. Сбой `core` задерживает выдачу: заявка остаётся в `SIGNED`, выдача повторяется, пока АБС не ответит. Если при сбое ЕГРЮЛ клиент открывает профиль компании, API возвращает последние сохранённые данные.

**Своя тестовая компания** — `POST /api/admin/companies`, только `ADMIN`. По компактному описанию симулятор создаёт данные компании во всех внешних системах, а в базе появляются компания и пользователь-руководитель с правом подписи; под его логином можно сразу войти и подать заявку. Исход заявки не задаётся — его считает конвейер по общим правилам. Все поля, кроме `name`, необязательны: по умолчанию получается устойчивая компания. Деньги — целые рубли, доли — числами (`0.12` — рост на 12 %), срок с регистрации и счёта — в месяцах; у ИП отчётности ГИР БО нет; `company_status` — `ACTIVE` или `LIQUIDATING`. ## Поток событий (SSE)

`GET /api/stream` — поток Server-Sent Events: интерфейс обновляется без перезагрузки страницы. Токен передаётся **только** в заголовке `Authorization: Bearer <token>`, в адресе он не принимается — так токен не попадает в логи. Стандартный `EventSource` браузера заголовки не передаёт, поэтому интерфейс читает поток через `fetch` ([frontend/src/api/stream.ts](../frontend/src/api/stream.ts)).

```bash
TOKEN=$(curl -s http://localhost:8080/api/auth/login -H 'Content-Type: application/json' \
  -d '{"login": "veter", "password": "demo"}' | jq -r .token)
curl -N http://localhost:8080/api/stream -H "Authorization: Bearer $TOKEN"
```

Поток клиента `veter` при отправке заявки и автоматическом одобрении (запись со стенда, часть однотипных событий опущена):

```text
retry: 3000

: ping

id: 29
event: message
data: {"id": 29, "kind": "STATUS_CHANGED", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "Заявка отправлена", "notify": false}

id: 30
event: message
data: {"id": 30, "kind": "STATUS_SUBMITTED", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "Заявка № 2026-00003 отправлена", "notify": true}

id: 31
event: message
data: {"id": 31, "kind": "STATUS_CHANGED", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "Проверяем заявку", "notify": false}

id: 32
event: message
data: {"id": 32, "kind": "PIPELINE_STEP", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "PIPELINE_STEP", "notify": false}

id: 39
event: message
data: {"id": 39, "kind": "STATUS_CHANGED", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "Предложение готово", "notify": false}

id: 40
event: message
data: {"id": 40, "kind": "STATUS_OFFER", "application_id": "74deba13-28af-41b2-89d9-8a80aef68715", "title": "Предложение по заявке № 2026-00003 готово", "notify": true}
```

Формат:
- первой строкой сервер присылает `retry: 3000` — пауза перед переподключением;
- событие — `id` (сквозной номер), `event: message` и `data` с JSON: `id`, `kind`, `application_id`, `title`, `notify`;
- раз в 15 секунд приходит комментарий `: ping`, чтобы соединение не закрывалось;
- новые события сервер проверяет раз в секунду.

Получив событие, интерфейс перечитывает затронутые данные: карточку заявки по `application_id`, очередь, ленту уведомлений. События с `notify: true` попадают и в ленту `GET /api/notifications` вместе с текстом `body`.

| `kind` | Кому | `notify` | Когда |
|---|---|---|---|
| `STATUS_CHANGED` | Клиенту и банку | нет | Любая смена статуса; `title` — новый статус для клиента |
| `STATUS_<статус>` | Клиенту | да | Статусы `SUBMITTED`, `NEED_INFO`, `MANUAL_REVIEW`, `OFFER`, `REJECTED`, `SIGNING`, `ISSUED`, `EXPIRED` |
| `STATUS_<статус>` | Банку | да | Статусы `MANUAL_REVIEW`, `ACCEPTED`, `DECLINED`, `CANCELLED` |
| `PIPELINE_STEP` | Клиенту и банку | нет | Шаг конвейера завершился или ждёт источник |
| `UPDATED` | Клиенту и банку | нет | Загружен или удалён документ |
| `INFO_ANSWERED` | Банку | да | Клиент ответил на запрос |
| `MESSAGE` | Другой стороне | да | Новое сообщение в чате |
| `SOURCE_WAITING` | Банку | нет | Шаг начал ждать внешний источник |
| `SOURCE_FAILED` | Банку | да | Источник недоступен дольше лимита |
| `DISBURSE_RETRY` | Банку | да | Выдача кредита повторяется из-за сбоя АБС |
| `JOB_FAILED` | Банку | да | Задание конвейера не выполнилось после всех попыток |

Клиент получает события только своей компании, сотрудники банка — события для банка по всем заявкам.

**Переподключение.** Без заголовка `Last-Event-ID` поток начинается с текущего момента. Чтобы не пропустить события за время обрыва, передайте номер последнего полученного события — сервер пришлёт всё, что было после него:

```bash
curl -N http://localhost:8080/api/stream -H "Authorization: Bearer $TOKEN" -H "Last-Event-ID: 44"
```

Сброс демо-данных не начинает нумерацию событий заново, поэтому открытые вкладки после сброса продолжают получать события без перезагрузки.

nginx проксирует поток без буферизации, таймаут чтения — час ([frontend/nginx.conf](../frontend/nginx.conf)); пинги не дают соединению простаивать.

## Внутренний API симулятора

> **Внутренний API.** Симулятор не опубликован наружу: у сервиса `simulator` нет проброшенных портов в [docker-compose.yml](../docker-compose.yml), а nginx ([frontend/nginx.conf](../frontend/nginx.conf)) проксирует только `/api/` в сервис `api`. Симулятор доступен лишь внутри сети Docker по адресу `http://simulator:8100`. Его вызывают `worker` (шаги конвейера и выдача) и `api` (профиль компании и управление сбоями). Для показа сбоев используйте `/api/admin/simulator/faults`.

Симулятор ([simulator/sim/main.py](../simulator/sim/main.py)) заменяет внешние системы синтетическими данными 10 тестовых компаний ([simulator/sim/data/companies.json](../simulator/sim/data/companies.json)) и компаний, созданных администратором в конструкторе ([simulator/sim/companies.py](../simulator/sim/companies.py)). Даты в ответах считаются от текущего дня, поэтому сценарии не устаревают. Контракты упрощены, смысл интеграций сохранён.

| Метод | Путь | Система | Что возвращает |
|---|---|---|---|
| `GET` | `/health` | — | `{"status": "ok"}` |
| `GET` | `/egrul/{inn}` | ЕГРЮЛ / ЕГРИП | Название, форма (`OOO` или `IP`), ОГРН, дата регистрации, статус (`ACTIVE`, `LIQUIDATING` и др.), ОКВЭД, адрес, руководитель и дата его назначения |
| `GET` | `/fns/{inn}` | ФНС «Прозрачный бизнес» | Налоговая задолженность, массовый адрес, дисквалификация руководителя, численность, налоговый режим |
| `GET` | `/girbo/{inn}` | ГИР БО | Выручка, прибыль от продаж и чистая прибыль за два последних года. Для ИП и компаний без отчётности — `{"available": false, "years": []}` |
| `POST` | `/bki/report` | Бюро кредитных историй | Тело `{"inn", "consent_id"}`; без согласия — 400. Наличие истории, максимальная просрочка за 24 месяца, текущая просрочка, действующие кредиты: кредитор, вид, сумма, остаток, платёж, дата |
| `GET` | `/bank/clients/{inn}` | Внутренние данные банка | Клиент ли банка, дата открытия счёта, поступления по месяцам за 12 месяцев. Не клиент — `{"is_client": false, "months": []}` |
| `POST` | `/core/loans` | АБС, выдача кредита | Тело `{"inn", "application_number", "amount", "rate", "term_months"}`. Номер ссудного счёта, время перечисления, `"status": "DISBURSED"` |
| `GET` | `/admin/faults` | Управление | Режимы всех систем |
| `PUT` | `/admin/faults/{source}` | Управление | Тело `{"mode", "latency_ms"}`; неизвестная система — 404 |
| `POST` | `/admin/faults/reset` | Управление | Все системы в режиме `ok` |
| `GET` | `/admin/companies` | Справка | ИНН, название и сценарий каждой тестовой компании, включая созданные |
| `POST` | `/companies` | Конструктор | Тело — описание компании (как `POST /api/admin/companies`, плюс `okved_name`). Создаёт персону во всех системах: ИНН и ОГРН с верными контрольными цифрами (префикс `0020`), ЕГРЮЛ, ФНС, ГИР БО, БКИ и банк. Ответ 201: `inn`, записи `egrul` и `bank` как у `GET /egrul/{inn}` и `GET /bank/clients/{inn}`. Сбои на регистрацию не действуют |
| `GET` | `/companies/{inn}` | Конструктор | Персона целиком в формате `companies.json` — и встроенная, и созданная; у созданных есть `spec` и `custom: true` |

Созданные персоны живут в памяти и дописываются в файл `SIMULATOR_CUSTOM_FILE` (в compose — `/home/app/custom_companies.json` в томе `simdata`), поэтому переживают перезапуск; если файл записать нельзя, симулятор пишет предупреждение в лог и держит их до перезапуска.

Неизвестный ИНН — 404 «Компания с таким ИНН не найдена в реестре»: конвейер передаёт такую заявку аналитику. Режимы сбоев — те же, что в разделе [«Управление демо-стендом»](#управление-демо-стендом). Обычная задержка ответа: ЕГРЮЛ 300 мс, ФНС 250 мс, ГИР БО 300 мс, БКИ 600 мс, банк 200 мс, АБС 400 мс, разброс ±30%. Множитель задержки задаёт переменная `SIMULATOR_LATENCY_SCALE`.
